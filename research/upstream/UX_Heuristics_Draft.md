# D4 · UX Heuristics（启发式层）草案

- 交付物：D4｜版本：v0.1 草案｜日期：2026-08-25
- 定位：给 AI Coding/Design Agent 消费的经验性判断工具集，供启发式评估（Heuristic Evaluation, HE）、设计评审与生成后自检调用；姊妹文档 D3 承载 Universal 原则层。
- 输入：dim02–dim05 研究简报、跨维度洞察与交叉验证报告；来源一律以 Source Registry 全局 ID 标注。
- 条目计数：启发式 31 条（H-01…H-31）＋神话隔离区 9 条。

## 0. 方法论说明

**什么是 heuristic。** 启发式是从大量真实可用性问题中归纳出的"足够好"的判断工具：Nielsen 的 10 条即由 249 个可用性问题 × 101 个候选启发式的因子分析萃取而来 [N039]。Nielsen 本人的定义边界是"broad rules of thumb, not specific usability guidelines"——它们用来**发现问题**，不是用来机械验证合规的规范 [A050]。其认识论地位是经验归纳而非科学定律：适用面广，但允许违反，违反是否成立由评估者在具体情境中判断。

**与 D3 原则（Principle）的三个区分判据**：① 证据等级——D3 只收 N/A 级证据且可还原到认知/知觉不变量的命题；本层收录 B/C 级证据（平台规范、产品实践、惯例史）或实证基础被原作者自认薄弱（如渐进披露 [B042]）但实践上有用的条目；② 可否违反——原则的反适用条件可显式枚举，启发式的例外是开放的，"什么时候该违反它"本身就是本层条目的必填字段；③ 判断方式——原则支持命题式判定，启发式只支持评审式提问：每条给出"评估问题"而非"通过条件"。

**正确使用方式**。HE 的效度依赖三条方法论纪律，全部来自原始文献：多名评估者**独立**评估后取并集（单评估者覆盖率严重不足，evaluator effect）[A022]；严重性用 0–4 量表且单人评级不可信、3 名评估者均值在实践中可用 [A017]；启发式不作 hard rule——条目之间的张力（可见性 vs 信噪比 vs 专家效率）是设计权衡本身，清单不提供裁决 [A050]。对 LLM 评估器，检测一致性 κ≈0.50 可用、严重性判断 α≈0 必须人工复核 [C006]（详见第 3 节）。

**收录范围**。本层承接 D3 §9.2 降级清单（渐进披露、8pt grid、16 顶层选项、whitespace、CPL/type scale、serial position、undo toast 参数、command palette、inline editing），不重复收录 D3 已立的 29 条原则；每条"与 Universal 原则的关系"字段标明它是某原则的启发式近似还是独立经验。

## 1. 核心启发式集

### 1.1 Nielsen 10 条的 Systemsmith 改编（H-01 … H-10）

以下 10 条是 Nielsen 10 [A050] 面向专业开发者工具语境的评审化改写：陈述保持原意，评估问题重写为对日志浏览器、查询构建器、仪表盘、命令面板等形态可直接提问的形式；"改编"仅指评估问题层，启发式本体未动。

### H-01 系统状态可见
- **ID / 来源**：H-01｜Nielsen 1994 #1 [A050]，Systemsmith 改编
- **陈述**：系统应在合理时间内让用户知悉正在发生什么，包括后台与异步过程。
- **评估问题**：① 用户能否在 3 秒内判断查询/索引构建/同步是否仍在进行？② 当前数据的 freshness（时间窗、采样率、更新时刻）是否可见？③ 静默失败时列表是否带有陈旧标记而非停在旧数据？
- **适用 scope**：所有存在时延的系统；可观测性与数据工具为强制级。
- **自动化可能性**：assistive——loading/empty/error/stale 四态覆盖可做运行时静态检查；状态"是否可感知"需评审判断 [C006]。
- **已知例外**：<100ms 完成的微操作无需指示（多余指示是噪音）；状态可见≠状态打扰。
- **与 Universal 原则的关系**：P-11 的启发式近似；与 P-13（变化主动 signaling）配套提问。

### H-02 系统语言匹配用户世界
- **ID / 来源**：H-02｜Nielsen 1994 #2 [A050]，Systemsmith 改编
- **陈述**：界面说用户的语言而非实现的语言；遵循现实世界的概念与顺序。
- **评估问题**：① 导航与标签是否使用用户领域词汇（SQL/PromQL/trace span 对开发者就是"现实世界"）？② 是否出现把内部 job ID、微服务名、数据库表名直接暴露在用户面？③ 默认值与排序是否符合领域惯例？
- **适用 scope**：所有产品；多角色产品需按角色分别提问。
- **自动化可能性**：assistive——工程词汇词表可做 LLM 初筛，但"这是谁的词汇"需领域判断。
- **已知例外**：专家工具的通用惯例（如 IDE 键位、kubectl 语法）本身就是用户语言，不应"翻译"成通俗词。
- **与 Universal 原则的关系**：P-19（系统映像）的评审侧提问；与 H-24（标签即气味）联动。

### H-03 用户控制与自由
- **ID / 来源**：H-03｜Nielsen 1994 #3 [A050]，Systemsmith 改编
- **陈述**：为误操作提供明确出口；支持撤销与重做；长操作可中断。
- **评估问题**：① 长查询/导出能否取消？② 删除、移动、覆盖类操作是否有 undo 或回收站兜底？③ 误入的视图能否一次返回（ Escape、面包屑、关闭键是否都在预期位置）？
- **适用 scope**：对象操作密集的桌面/Web 工具；移动端正文操作同样适用。
- **自动化可能性**：assistive——undo/取消入口的存在性可检查；恢复的正确性必须运行时验证。
- **已知例外**：真正不可逆操作（转账、全员发布、无备份的 DROP TABLE）用确认而非 undo；假 undo 比确认框更糟。
- **与 Universal 原则的关系**：P-14 的启发式近似；实现参数见 H-29。

### H-04 一致性与标准
- **ID / 来源**：H-04｜Nielsen 1994 #4 [A050]，Systemsmith 改编
- **陈述**：同一对象、动作、状态在全系统同名、同编码、同行为；遵循平台与行业惯例。
- **评估问题**：① 同一概念是否三处三个名字（run/execution/job）？② 同一图标在不同模块是否含义漂移？③ 键位与交互是否服从所在平台与行业惯例（IDE 键位、Git 词汇、Ctrl/Cmd+K）？④ 有意打破一致处是否有可辩护理由（如只读/编辑模式区分）？
- **适用 scope**：多模块、多团队共建的大型工具尤其适用。
- **自动化可能性**：deterministic 部分可做——术语/标签/图标一致性可词典驱动 lint [C030]；行为一致性 assistive。
- **已知例外**：一致性不能凌驾上下文合理性；"一致的坏设计"不值得保留。
- **与 Universal 原则的关系**：P-17（内部）与 P-18（外部惯例）的合并评审版——HE 实践中两层通常一次走完。

### H-05 错误预防
- **ID / 来源**：H-05｜Nielsen 1994 #5 [A050]，Systemsmith 改编
- **陈述**：先消除易错条件（约束、默认值、即时校验），再依赖错误信息；区分 slips 与 mistakes，干预点不同。
- **评估问题**：① 破坏性/批量/生产环境操作是否有约束或二次确认（输入库名确认 DROP TABLE）？② 表单与查询输入是否即时校验并标出出错位置？③ 多模式界面（查看/编辑）的模式状态是否有强 signifier（防 mode error）？④ 禁用提交按钮时是否说明缺少什么？
- **适用 scope**：破坏性、批量、生产环境操作为强制级；所有表单适用。
- **自动化可能性**：assistive——约束与校验的存在性可静态检查；slip 诱发性需用户测试。
- **已知例外**：探索性操作不应被过度防呆扼杀；专家需要 escape hatch。
- **与 Universal 原则的关系**：P-15 的启发式近似。

### H-06 再认优于回忆
- **ID / 来源**：H-06｜Nielsen 1994 #6 [A050]，Systemsmith 改编
- **陈述**：让对象、动作、选项可见可选，把凭记忆输入的任务转化为从候选中认出的任务。
- **评估问题**：① 命令、查询、配置功能是否可从列表/补全/面板中发现，而非要求背语法？② facet 值是否陈列而非空输入框？③ 历史记录、最近文件、查询历史是否可复用？④ 是否存在要求用户背 trace ID 才能查询的路径？
- **适用 scope**：新手与低频用户界面为高优先级；功能面大的专业工具全面适用。
- **自动化可能性**：assistive——候选可见性可评审；发现时间需实测。
- **已知例外**：专家高频操作允许回忆路径（练习摊销成本），但不得是唯一路径；口令/密钥不应被"提示"。
- **与 Universal 原则的关系**：P-06 的启发式近似；与 H-20（命令可发现性）是同一命题的两个入口。

### H-07 灵活性与效率
- **ID / 来源**：H-07｜Nielsen 1994 #7 [A050]，Systemsmith 改编
- **陈述**：为专家提供不增加新手负担的加速通道——快捷键、命令面板、批量操作、脚本化。
- **评估问题**：① 高频操作是否有键盘/命令面板路径？② 加速通道是否可发现（列表项提示键位、? 键位表）？③ 批量场景是否有批量选择与批量操作，还是让专家逐行点击 200 次？④ 加速通道是否是功能的唯一入口（若是则为违规）？
- **适用 scope**：高频使用的专业工具；低频消费级界面可跳过本条。
- **自动化可能性**：assistive——通道存在性可检查；加速收益需专家任务计时。
- **已知例外**：加速通道允许对新手隐藏，但须存在可发现入口；hidden affordance 只允许存在于加速层。
- **与 Universal 原则的关系**：P-24 的启发式近似；与 P-20 的可见性折中配套。

### H-08 信噪比
- **ID / 来源**：H-08｜Nielsen 1994 #8 [A050]，Systemsmith 改编（纠错性重述）
- **陈述**：削减与任务无关的元素，而非削减信息量；每个信息单元都在与同级单元竞争注意。
- **评估问题**：① 屏上每个元素能否说出它服务的任务？② 高饱和色、阴影、渐变等装饰是否在与 status 语义争夺前注意通道？③ 密度是否由分组、对齐、层级与语义色支撑，还是"无结构的密"？④ 是否存在为求"简洁"而砍掉专家并行吞吐的极简改造？
- **适用 scope**：dashboard、日志/指标/trace 浏览器、数据表格等专家高频工具；消费级首屏反向适用（极简优先）。
- **自动化可能性**：assistive——装饰性元素与语义色密度可部分静态审计 [C007]；相关性判断需评审。
- **已知例外**：新手 onboarding 流程与营销场景不适用密度论证；企业场景的效率指标是 time-on-task 与 error rate 而非 engagement [A053]。
- **与 Universal 原则的关系**：P-10 的启发式近似（本条是对 Nielsen #8"minimalist"流行误读的纠正：原文是信噪比，不是少即是多 [A050]）。

### H-09 错误诊断与恢复
- **ID / 来源**：H-09｜Nielsen 1994 #9 [A050]，Systemsmith 改编
- **陈述**：错误信息用用户语言精确指出问题并给出建设性下一步；保留用户已输入的内容。
- **评估问题**：① 错误信息是否回答"发生了什么 + 为什么 + 下一步做什么"？② 错误码是否是唯一信息（对开发者：可搜索的错误码 + 文档链接才是正解，而非"不要错误码"）？③ 报错后表单输入是否被保留？④ 错误是否就地显示在出错字段旁而非汇总到他处？
- **适用 scope**：所有表单、查询、执行路径；API 错误响应同样适用。
- **自动化可能性**：assistive——错误文案模式可 LLM 初筛；恢复流程有效性需走查或用户测试。
- **已知例外**：安全敏感场景（认证失败）有意模糊错误细节。
- **与 Universal 原则的关系**：独立经验——P-15 管预防，本条管预防失败后的恢复质量，两者互补不重合。

### H-10 帮助与文档
- **ID / 来源**：H-10｜Nielsen 1994 #10 [A050]，Systemsmith 改编
- **陈述**：最好无需文档即可使用；必须有的帮助应可搜索、面向任务、步骤具体、就近嵌入。
- **评估问题**：① 复杂概念（metric 定义、查询语法）是否有上下文内嵌解释（hover/inline docs）？② 文档是否按用户任务组织而非按系统模块组织？③ 空状态与错误信息是否链向对应文档？④ 文档搜索能否用用户的词找到内容（文档可检索性同样是信息气味问题）？
- **适用 scope**：学习曲线陡的专业工具、查询语言、配置系统。
- **自动化可能性**：manual-only——文档质量与任务匹配度本质是内容评审。
- **已知例外**：自解释性强的界面不应为"有文档"而堆砌引导；onboarding 教学弹窗不是文档的替代品。
- **与 Universal 原则的关系**：独立经验；文档检索性与 P-21（信息气味）共享机制。

### 1.2 视觉与排版经验法则（H-11 … H-18）

本组来自 D3 §9.2 降级清单与 dim04 视觉惯例层：性质为 design heuristic 或工业惯例，未达 Universal 证据门槛，但均是评审"专业感"的高产出提问点；dim04 的结构性归因（层级不清→对齐失锚→节奏混乱→装饰竞争→容器滥用→数字排版业余）是本组的问题发现骨架 [A018][A054][A025]。

### H-11 对齐锚点
- **ID / 来源**：H-11｜工业实践（CRAP 的 Alignment 条 [A054] + 网格系统传统 [A025]），教学法层
- **陈述**：每个元素应与某个共享边或中心线建立视觉连接；无锚点的元素被感知为"随机摆放"。
- **评估问题**：① 逐块检查：该元素与哪条共享边/中心线对齐？答不上来即疑似失锚。② 同列数据、标签与控件是否共享左缘或右缘？③ 面板、卡片、标题的边界是否落在同一组垂直线上？
- **适用 scope**：所有视觉呈现；密集表格与表单为高发区。
- **自动化可能性**：deterministic——边界盒坐标一致性可静态 lint（dim04 A7 表判定可自动）。
- **已知例外**：刻意的破网格（breakout）用于强调是合法手法，但一屏至多一处；图表内部数据元素按数据定位，不受版心网格约束。
- **与 Universal 原则的关系**：P-01（分组）与 P-03（层级）的工艺层近似——对齐是最廉价的分组与秩序信号。

### H-12 间距基数纪律
- **ID / 来源**：H-12｜工业惯例：8pt grid（Material 2014 [B013]；命名与普及 [B034]）；证据状态：工程惯例，无感知实证
- **陈述**：间距取值应合同一基数（如 4/8pt 倍数体系），组件内细间距可用半基数；基数体系的价值在工程可执行性与跨密度整数缩放，不在感知最优。
- **评估问题**：① 抽查相邻元素间距，是否出现基数之外的"野值"（13px、19px）？② 间距是否经 token 引用而非硬编码？③ 垂直节奏（行高、段落间距）是否与基数体系一致？
- **适用 scope**：有 token 体系的设计系统；营销页与艺术指导场景可放宽。
- **自动化可能性**：deterministic——spacing token lint 可确定性执行（dim04 B8-3 表）。
- **已知例外**：网格列宽、图片对齐、光学修正需要破例——"规则是默认值，不是定律" [B034]；不得把 8pt 当"spacing→可用性"的因果依据引用。
- **与 Universal 原则的关系**：独立惯例——P-10（结构化密度）的容积率实现手段之一，但本身不携带感知证据。

### H-13 容器纪律
- **ID / 来源**：H-13｜工业实践 + NN/g 研究型文章 [A018]
- **陈述**：common region（边框/背景容器）是最强也最贵的分组线索；默认用低成本手段分组（留白→对齐→分隔线→背景块→边框容器），把容器留给真正需要"模块化实体感"的内容。
- **评估问题**：① 屏上是否存在"卡片套卡片"？② 每个容器的边界、padding、背景三层开销换来了什么分组信息？③ 如果所有内容都被框住，分组信号是否已自相抵消？④ 该容器能否用留白或分隔线替代而不损失结构？
- **适用 scope**：dashboard、面板密集的工具界面为高发区。
- **自动化可能性**：assistive——嵌套容器深度与边框计数可静态检测；"是否过度"需评审（NN/g 判定："Overuse Creates Clutter" [A018]）。
- **已知例外**：拖放目标、可独立操作的模块（dashboard widget）、需要 figure-ground 反转的强调区（如告警横幅）合法使用强容器。
- **与 Universal 原则的关系**：P-01 的成本侧近似——分组线索成本递增，容器滥用同时击穿 P-10 信噪比。

### H-14 数字排版
- **ID / 来源**：H-14｜平台规范级惯例 [B037]
- **陈述**：数据列、指标、计时器等纵向比较的数字应启用 tabular figures（`tabular-nums` / OpenType `tnum`）；行文中的数字用 proportional figures。
- **评估问题**：① 表格数字列是否等宽对齐、可纵向扫描？② 动态刷新的数字是否因字宽变化产生布局抖动？③ 单位与精度在同列是否一致？
- **适用 scope**：数据表格、监控面板、财务界面；纯文本叙述不适用。
- **自动化可能性**：deterministic——CSS feature 检测可自动执行（dim04 B8-3 表）。
- **已知例外**：大标题中的展示性数字（big number）可用 proportional 以追求字形美感。
- **与 Universal 原则的关系**：P-01/P-10 的排版实现层——等宽数字是对齐与纵向分组的前提条件。

### H-15 字号层级梯度
- **ID / 来源**：H-15｜教学法共识（type scale 传统，dim04 判定惯例层；D3 §9.2 降级记录）
- **陈述**：文本层级（标题/分区/正文/辅助）应构成无歧义的显著性梯度；相邻层级差异必须大到不会被误读为噪差——"几乎相同"的两级被感知为错误而非层级。
- **评估问题**：① 遮住内容只看字级，能否在 3 秒内排出阅读顺序？② 是否存在"差不多大"的相邻两级标题？③ 层级信号是否只靠颜色深浅单一通道（消耗对比度预算）？④ 全屏字级是否超过 4–5 级（梯度被摊薄）？
- **适用 scope**：所有文本界面；dense 工具中层级应靠字重/位置而非面积（与 P-03 的张力记录一致）。
- **自动化可能性**：assistive——字级数量与比率可静态提取，"梯度是否可辨"需视觉评审或 MLLM-as-judge 加人工校准 [C034]。
- **已知例外**：刻意的等权陈列（grid of equals）是合法设计；具体 type scale 比率（1.25/1.333 等）无实证，不作检查项。
- **与 Universal 原则的关系**：P-03 的排版近似。

### H-16 行宽与行高
- **ID / 来源**：H-16｜排版工艺共识 + 弱实证（45–75 CPL、行高 1.4–1.6×；边界值弱实证；registry 未收录其一手来源，D3 §9.2 记录）
- **陈述**：正文块行宽宜保持在约 45–75 字符区间，行高约字号的 1.4–1.6 倍；区间方向可靠，边界数字不可外推为硬规则。
- **评估问题**：① 正文段落是否被拉满整个超宽容器（>100 CPL）？② 行距是否随字号联动而非固定像素？③ 多栏布局中每栏行宽是否仍在区间内？
- **适用 scope**：文档、设置说明、长文本区；表格单元格与标签不受 CPL 约束。
- **自动化可能性**：deterministic——容器宽度与字号可计算 CPL 估算值；阅读舒适度仍需人工。
- **已知例外**：窄侧边栏、表格内文本天然低于 45 CPL，不是问题；东亚文字 CPL 换算不同，数字仅作方向参考。
- **与 Universal 原则的关系**：独立惯例——P-26/P-27 管可读性合规地板，本条管地板以上的排版舒适区。

### H-17 留白方向性
- **ID / 来源**：H-17｜改编自小样本实证 [B030]（n=20；方向可用、效应量不可外推，Low）
- **陈述**：页边距与元素间留白大于零对阅读速度与理解有正向作用；行距主要影响偏好而非绩效。
- **评估问题**：① 内容是否顶到视口/容器边缘（margin=0）？② 分组之间的留白是否显著大于组内留白（proximity 分组成立的前提）？③ 为塞入更多内容而清零留白的地方，是否正是扫描最吃力的区域？
- **适用 scope**：文本与表单密集区；专业工具的"紧凑模式"应削减的是行高与 padding 档位，不是清零留白。
- **自动化可能性**：assistive——零边距与组间/组内间距比可静态检测。
- **已知例外**：数据表格的行内密度不受本条约束；任何"whitespace +20% 理解率"式精确数字引用应拒绝（n=20 小样本，见神话隔离区）。
- **与 Universal 原则的关系**：P-01（proximity 分组）的间距近似。

### H-18 视觉尺寸 ≠ 交互热区
- **ID / 来源**：H-18｜平台惯例抽象（M3 小尺寸组件仍保持 ≥48dp 热区的规则 [E031]；合规地板 [N002]）
- **陈述**：控件的视觉呈现可以小，其指针热区必须满足地板并预留操作余量；图标按钮应外扩透明热区（24px 合规地板，icon-only 40–48px 为 best practice 层）。
- **评估问题**：① 16px 图标的实际 hit area 是多大？② 数据行内的 hover 操作是否要求像素级瞄准？③ 相邻热区是否相交或间距不足？④ 触屏交付物是否把桌面的小热区直接搬了过去？
- **适用 scope**：指针与触屏双端；高密度表格行内操作为高发区。
- **自动化可能性**：deterministic——几何测量可自动 [N002]。
- **已知例外**：文本内联链接按排版自然热区计；画布内的数据点瞄准用放大/套索等补偿机制而非扩大每个点。
- **与 Universal 原则的关系**：P-27（数值地板）与 P-09（Fitts）之间的实践层——地板以上、最优以下的工程余量。

### 1.3 专业工具特有启发式（H-19 … H-22）

本组为 dim 研究在专业工具语境下新立的条目，证据形态为产品实践收敛（C 级）+ 机制推论，是本层中证据最年轻但场景适配最强的一组。

### H-19 密度一致性
- **ID / 来源**：H-19｜工业实践收敛（EUI allowDensity [C009]、Spectrum 2 可定制密度 [C041]、Fluent 密度模式 [B014]；密度成本实证为 AR 单研究、外推降权 [C029]）
- **陈述**：密度是一等设计维度且应在产品内一致：同类表面同密度档位；提供密度切换时，档位差应体现在行高/padding/字号阶梯而非个别元素的即兴压缩。
- **评估问题**：① 相邻面板的行高与内边距是否同档？② 同一列表在不同页面是否密度漂移？③ 紧凑模式是否系统性映射 token 阶梯，还是逐元素手写缩小？④ 密度提升是否伴随结构信号（对齐、分组、语义色）的同步强化——无结构的密是违规。
- **适用 scope**：企业/开发者工具；消费级产品通常单密度，本条不适用。
- **自动化可能性**：deterministic 部分可做——行高/padding token 引用与档位映射可 lint；密度与任务匹配度 assistive。
- **已知例外**：强调区（告警横幅、big number 面板）刻意降密度是层级手段；onboarding 流程应独立于工作面密度。
- **与 Universal 原则的关系**：P-10 的操作化——"结构化密度"在工程层的形态即密度 token 纪律。

### H-20 命令可发现性
- **ID / 来源**：H-20｜成熟实践模式（命令面板跨产品主流化 [C057]，Low：无 HCI 期刊级实证）
- **陈述**：功能面大的工具应提供命令面板或等价的全局命令入口；面板内应提示键位、支持模糊匹配、按频率排序，且面板不替代可见导航。
- **评估问题**：① 不依赖文档，新用户能否发现命令面板的存在（菜单入口、快捷键提示）？② 面板是否同时服务跳转与动作执行？③ 结果排序是否按使用频率/相关性，还是字母序？④ 是否存在只在面板里、无任何可见入口的核心功能（发现性死路）？
- **适用 scope**：命令与对象数量大的键盘导向专业工具；低频消费级界面不适用。
- **自动化可能性**：assistive——入口存在性可检查；排序质量需行为数据。
- **已知例外**：功能面小的产品强加命令面板是冗余；命令面板增加回忆负担，对新手必须靠可见入口兜底（与 H-06 联动）。
- **与 Universal 原则的关系**：P-06 与 P-24 的交汇实践——把 recall 任务改写为 recognition 任务的具体形态。

### H-21 上下文保持
- **ID / 来源**：H-21｜改编（Shneiderman mantra 的 focus+context 推论 [N019]；证据状态 Medium：作者自述该文为 opinion piece [E023]，Craft & Cairns 指出其不可证伪 [A021]）
- **陈述**：查看细节不应离开所在上下文——详情用侧栏/展开/popover 而非整页替换；缩放与过滤时保留全局定位（minimap、面包屑、时间直方图）。
- **评估问题**：① 打开详情后，列表上下文是否仍在屏上？② 缩放 trace/时间轴时全局位置是否可见？③ 从详情返回列表，滚动位置与过滤状态是否保留？④ 模态是否遮住了被比较的对象？
- **适用 scope**：数据探索、日志/trace/指标浏览器、画布类工具；单任务向导流不适用。
- **自动化可能性**：assistive——导航替换 vs 就地展开的结构可静态分析；上下文充分性需评审。
- **已知例外**：沉浸式任务（写作、演示）刻意排除上下文是合法的；用户带明确目标进入时 search-first 优于 overview-first [A021]。
- **与 Universal 原则的关系**：P-23 的评审侧近似（P-23 本身按 Medium 置信度使用，本条随行标注）。

### H-22 状态可分享与历史可回放
- **ID / 来源**：H-22｜改编（mantra 的 history/extract 任务 [N019]，同一 Medium 证据状态）
- **陈述**：分析型工具的全部视图状态（过滤、时间窗、选中、缩放区间）应编码进 URL 或等价物，可分享、可恢复；操作历史可回放。
- **评估问题**：① 复制当前 URL 发给同事，对方能否看到完全相同的视图？② 过滤条件是否以可移除 chips 呈现且可逆？③ 刷新/前进/后退是否保持状态？④ 分析路径能否回放或导出（查询参数提取）？
- **适用 scope**：可观测性、数据探索、报表工具；一次性消费内容不适用。
- **自动化可能性**：deterministic 部分可做——URL 状态编码的完备性可脚本化比对。
- **已知例外**：含敏感信息的视图状态不应进 URL；高频交互态（hover）不值得编码。
- **与 Universal 原则的关系**：P-23 的下半句——history 与 extract 是专业工具与普通 dashboard 的分水岭 [N019]。

### 1.4 IA 与交互经验法则（H-23 … H-31）

### H-23 宽浅结构方向性
- **ID / 来源**：H-23｜经典实证的二手转述（Larson & Czerwinski 1998，经 HFI 综述 [B017]，Low：1998 Web 语境，精确数字不可外推）
- **陈述**：导航层级设计的方向是"宽而浅优于窄而深"——分类决策比视觉扫描更费认知；"约 16 个顶层选项 × 2–3 层"只作方向参考，不作目标值。
- **评估问题**：① 是否存在把常用功能压进三层深菜单的结构？② 顶层选项的标签区分度是否足够（首层 scent 是第一杠杆）？③ 层级深度增加是换来了真实分类收益，还是只为"显得简洁"？
- **适用 scope**：菜单、设置、文档站等信息架构评审。
- **自动化可能性**：assistive——树深度/广度可计算；scent 质量需评审或 tree testing [N033]。
- **已知例外**：串行任务流（向导）天然是深结构；超大语料库需要更深的受控词表。引用本条时必须带 Low 标注与年代语境。
- **与 Universal 原则的关系**：P-08（Hick）与 P-21（scent）的经验近似——分类结构降低熵才是宽浅优越的真实机制。

### H-24 标签即气味
- **ID / 来源**：H-24｜工业实践 + 理论底座（信息觅食 [N018]；action label 词典化 [C030]）
- **陈述**：导航质量的日常杠杆是标签措辞：标签用用户词汇、含 trigger words、动作标签带对象（"New user" 而非 "New"）、具体动词优先于裸 "OK"；同一功能全系统同一标签。
- **评估问题**：① 遮住页面其余部分，仅凭链接/按钮文字能否预测其后内容？② 标签是用户词汇还是工程词汇（"ResourceInstance 管理"）？③ 对话框主按钮是否写清动作而非 "OK"？④ 同一动作的命名在菜单、按钮、文档中是否一致？
- **适用 scope**：所有导航、命令、对话框；错误码与文档标题同样是 scent 载体。
- **自动化可能性**：deterministic 部分可做——词典 lint [C030]；scent 强度判断 assistive（LLM 初筛 + tree testing 验证）。
- **已知例外**：惯例化图标（搜索放大镜、设置齿轮）在空间极紧处可独存，但核心导航不应纯图标无文字。
- **与 Universal 原则的关系**：P-21 的工艺层近似；一致性维度归 P-17。

### H-25 Facet 纪律
- **ID / 来源**：H-25｜多源实践收敛 [C021][C020]
- **陈述**：facet 来自内容模型与用户研究而非 UI 团队想象；facet 内 OR、facet 间 AND；已选条件以可移除 chips 显示；显示计数；零结果值置灰禁用；覆盖率 <15% 条目的 facet 删除；facet 值默认显示前 5 个。
- **评估问题**：① 每个 facet 的取值覆盖率与区分度是否经过盘点？② 已选条件是否一眼可见、单个可移除、可一键清空？③ 选中组合导致零结果的路径是被禁用还是放用户走进死胡同？④ facet 顺序是否按区分度/使用频率？
- **适用 scope**：大目录、数据浏览器、搜索过滤。
- **自动化可能性**：deterministic 部分可做——AND/OR 逻辑、chips 存在性、零结果禁用可运行时检查；区分度盘点需数据分析。
- **已知例外**：受控词表极小的场景平铺全部取值即可；"前 5 值"是实现参数惯例，非定律。
- **与 Universal 原则的关系**：独立实践集——机制上服务 P-21（facet 名与取值是 scent 载体）与 P-05（chips 外化已选状态）。

### H-26 渐进披露
- **ID / 来源**：H-26｜Nielsen 2006 定义，源头 Carroll & Rosson "training wheels"；证据状态：作者自认无有效性证据（"empirical research lacking"）[B042]，反模式条件 [B043]
- **陈述**：把高级/低频功能推迟到次级界面以降低初始复杂度；分割点必须基于用户观察，次级入口的气味必须强，且避免多个通往次级的入口。
- **评估问题**：① 初始层与次级层的分割依据是什么数据（使用频率、角色）？② 用户能否发现次级层的存在与进入方式？③ 被推迟的功能是否其实需要并排比较（此时披露有害）？④ 额外步骤成本是否小于它降低的复杂度？
- **适用 scope**：新手/专家共存的表单、设置、仪表盘自定义；安全关键信息不得被披露层级隐藏。
- **自动化可能性**：manual-only——分割合理性依赖任务与频率分析。
- **已知例外**：需要同时对比全部信息时、隐藏安全关键信息时、额外步骤成本大于复杂度收益时，不应使用 [B043]；ad-hoc 使用必然失真 [B042]。
- **与 Universal 原则的关系**：独立经验——与 P-24 共享"新手/专家双速"动机，但实证基础远弱，引用时必须带证据状态。

### H-27 空状态回答"现在该做什么"
- **ID / 来源**：H-27｜实践收敛 + 企业规范 [E038][C055]
- **陈述**：空状态必须回答"用户现在该做什么"：headline + 情境化说明 + 单一 CTA；按 first-use / user-cleared / no-results / error 四型分别设计，不用通用占位。
- **评估问题**：① 该空状态属于四型中的哪一型，文案是否对症？② no-results 是否提供清除过滤/扩展搜索的出口？③ 是否给出三个以上模糊选项稀释行动？④ error 型是否带恢复路径？
- **适用 scope**：所有列表、dashboard、搜索；新用户首屏为高优先级。
- **自动化可能性**：assistive——空状态存在性与结构可检查；文案质量需评审。
- **已知例外**：user-cleared 型（全部完成）可以不设 CTA，成就确认即内容。
- **与 Universal 原则的关系**：独立实践——兼作 P-19 的投影（空状态在教用户"这个系统是干什么的"）。

### H-28 加载状态契约
- **ID / 来源**：H-28｜企业规范（Carbon Loading pattern [C055]）+ 惯例
- **陈述**：>1s 的等待给出骨架或进度；确定时长用 determinate 指示，不确定用 indeterminate 但不冒充进度；加载中保持布局稳定，不整页白屏替换上下文。
- **评估问题**：① 1 秒以上无反馈的路径有哪些？② indeterminate 进度条是否在伪装真实进度？③ 骨架屏是否反映最终布局（滥用骨架反而放大感知等待）？④ 局部刷新是否保住了未刷新区域的上下文？
- **适用 scope**：数据密集型工具的全部异步路径。
- **自动化可能性**：assistive——loading 态覆盖可运行时检测；感知质量需实测。
- **已知例外**：<100ms 微操作不加任何指示；实时流数据有自己的更新语义，不套加载契约。
- **与 Universal 原则的关系**：P-11 与 P-12 的实现层近似。

### H-29 可逆操作的实现参数
- **ID / 来源**：H-29｜模式实现参数（undo toast 时限、hover/focus 暂停计时、回收站兜底；"Clear all" 等细则 [C021]）
- **陈述**：undo toast 应有明确时限（约 10 秒量级）、时限可被发现、hover/focus 暂停倒计时、可键盘聚焦；慢速兜底（回收站/版本历史）作为第二层。
- **评估问题**：① toast 消失前用户是否有合理反应时间，键盘用户能否触达 undo？② 时限是否可调或符合时限可访问性要求？③ 回收站/历史是否真实存在且可恢复？④ "Clear all" 类批量操作是否有独立的防呆？
- **适用 scope**：实现了 P-14 可逆性架构的产品；无可恢复架构时本条全部不适用（先做架构）。
- **自动化可能性**：assistive——聚焦可达与暂停行为可脚本化测试；时限适当性需评审。
- **已知例外**：真正不可逆操作走确认而非 undo；高频微操作的 undo 走快捷键历史栈，不打 toast。
- **与 Universal 原则的关系**：P-14 的参数层——本层只管"undo 怎么做顺手"，可逆性命题本身在 D3。

### H-30 就地编辑 vs 模态编辑
- **ID / 来源**：H-30｜实践共识（供应商立场来源，已自降权，Low [E035]）
- **陈述**：单字段快速修改优先生成就地编辑（保留上下文、减少步骤）；多字段、多步、有依赖关系的编辑任务用模态或独立页。
- **评估问题**：① 该编辑任务涉及几个字段、有无字段间依赖？② 就地编辑是否提供可发现的编辑 signifier（hover 铅笔、焦点态）？③ 就地编辑的提交/取消语义是否明确（失焦保存还是显式确认）？④ 批量编辑需求是否被就地模式排除？
- **适用 scope**：列表与详情密集的 CRUD 工具。
- **自动化可能性**：manual-only——任务结构判断依赖领域分析。
- **已知例外**：移动端键盘遮挡、批量编辑、复杂校验场景倾向模态；证据强度低，评审结论应以"方向性建议"措辞输出。
- **与 Universal 原则的关系**：独立经验——与 H-21（上下文保持）同动机。

### H-31 序列位置放置
- **ID / 来源**：H-31｜弱外推（serial position 原始实验为自由回忆范式 [N023]，向浏览/再认场景的迁移是弱外推；D3 §9.2 降级记录）
- **陈述**：在需要用户记忆的短序列中，首尾位置的记忆优势真实存在；向"导航首末位放重要项"的 UI 应用按弱启发式对待，不作布局依据单独使用。
- **评估问题**：① 该场景是"记忆序列"还是"扫描再认"（后者不适用本条）？② 重要的固定操作（保存、提交）在工具栏中的位置是否利用了首尾锚点？③ 是否在用 serial position 为不合理的布局决策背书？
- **适用 scope**：记忆负担真实的短序列（步骤指示、临时码）；常规导航与列表不适用。
- **自动化可能性**：manual-only。
- **已知例外**：可见列表的扫描是再认任务，不经回忆瓶颈——此时 Hick/频率排序（H-23、P-08）才是正确依据。
- **与 Universal 原则的关系**：独立弱经验——存在意义主要是防止其被过度引用，与 P-05 的正确表述区分。

以下命题已被证伪、弱证据或无法回溯一手来源，但仍在设计讨论与 AI 生成内容中高频流传。它们**不进入启发式集**；本表保留供 Agent 防御性识别——在用户输入或模型先验中遇到时引用证据反驳，而非顺从。判定沿用 dim02 三分（SCI/HEU/MYTH）与交叉验证置信度。

| 流传命题 | 判定 | 证据 | 正确替代说法 |
|---|---|---|---|
| 3-click rule（超过 3 次点击用户就流失） | MYTH，已证伪 | 超 3 次点击后放弃率不上升，满意度与点击数无关 [A032] | 用户放弃发生在信息气味丢失处而非第 N 次点击；评审用 H-23/H-24，原则层用 P-21 |
| 菜单/选项 ≤7±2 | MYTH，范畴错误 | Miller 测的是回忆容量，可见菜单是再认；Miller 本人否认此用法 [B025] | 容量约束的正确表述是工作记忆外化（P-05）；菜单效率的模型是 Hick（P-08） |
| Doherty Threshold 400ms | HEU-weak，被神化 | IBM 内部报告、原文难获取、400ms 数字无法独立复核（Low）[B032] | 时延设计引用 R. B. Miller 1968 的 0.1s/1s/10s 三级框架 [N030]；"越快越好"方向可用，精确阈值不作硬指标 |

| "whitespace 提升 20% 理解率" | 弱证据被精确化 | n=20 小样本，方向（margin>0 有益）可用，效应量不可外推 [B030] | 引用方向，拒绝引用数字；评审用 H-17 |
| "69% 注意力在页面左上"等流传数字 | 营销数字 | 无法回溯可靠原始实验，dim04 已按营销数字处理、不予入库 | 初始注意分配由显著性梯度驱动（P-02/P-03），不存在固定百分比 |

## 3. HE 执行规程（Agent 启发式评估）

本节规定 Agent 以本层启发式集执行 HE 的操作流程。依据全部来自评估方法原始文献与 2025–2026 年 LLM 评估器量化研究。

**评估者配置：多评估者独立评估取并集。** HE 的方法论基石是单评估者覆盖率严重不足——不同评估者发现的问题子集几乎不重叠，必须多人独立评估后汇总去重 [A022]。覆盖率规划用 Nielsen & Landauer 的泊松模型：λ≈0.31，5 名评估者约发现 75% 问题，区间表述 2/3–85%；这是成本-收益规划估计而非定律 [N012]。对 Agent 的映射：用多个独立评审实例（不同 persona、不同启发式子集、不同遍历顺序）替代"单实例多跑几遍"——同一实例的重复评估不构成独立评估者。每个评估者至少遍历界面两遍：第一遍走任务流，第二遍逐区域对照启发式提问 [A022]。

**严重性评级纪律。** 0–4 量表（0=非问题，1=cosmetic，2=minor，3=major，4=catastrophe），严重性由 frequency × impact × persistence 合成；评级在全部问题汇总后独立进行，不在发现的同时评级。单人评级不可靠，3 名评估者均值在实践中可接受 [A017]；中间档难分是已知缺陷，有实践者直接缩减为三级量表 [B033]。Agent 输出严重性时必须标注评级者构成；单实例输出的严重性数值视为未评级。

**LLM 评估的已知边界。** 目前唯一对 LLM 启发式评估做了评估者间一致性量化的研究（GPT-4o、30 个开源网站、850+ 次评估）显示：问题**检测**一致性中等（pairwise Cohen's κ=0.50，exact agreement 84%），可用作存在性初筛；**严重性判断**不可靠（weighted κ=0.63 而 exact agreement 仅 56%，Krippendorff's α≈0），必须人工复核 [C006]。这与人类评估者的 evaluator effect 同构，也与其他 LLM-as-judge 研究的偏差记录一致（position/verbosity 偏差 [C033]；截图评审"流畅但证据薄弱" [C005]）。结构化 rubric 可显著提升评判可靠性（标注者间一致性 >80% [C034]）——本层每条的"评估问题"字段即 rubric 化设计，评审时应逐问引用而非凭整体印象打分。多模态绝对打分发散、成对比较可对齐 [A055]：视觉层级、节奏、色彩克制度类判断优先用"对比参照物"而非"打绝对分"。

**与自动化 lint 的分工。** 三层结构（dim04 B8-3 表固化）：① 确定性层（deterministic）——对比度、target size、spacing token、对齐坐标、tabular-nums、术语词典，由 axe-core 类规则引擎与 token lint 执行，零误报、可 fail 构建 [B001]；条目标注 deterministic 的部分不进 HE 会议，进 CI。② 半自动层（assistive）——启发式违规的存在性初筛，LLM 执行、携带"needs human review"标志，人去重与复核；③ 人工层（manual-only / empirical）——严重性终裁、任务匹配度、可学性（认知走查四问 [A023]，工程环境可用 Spencer 两问精简版 [B019]）、以及一切 outcome 类命题——任务成功率、满意度本质是"使用的结果"而非产品属性，必须真实用户 [N040]。Agent 的职责边界：自动化地板做确定，中间带做初筛并显式标注置信，天花板之上只做结构化呈现，不输出裁决。

**与 D7 验证枚举的映射**：本文 manual-only 细分两类——expert-review-only（专家评审即可，→ D7 validation.method = heuristic_review, automatable = partial）与 user-test-required（必须真实用户测试，→ D7 method = user_test, automatable = none，对应 D3 的 empirical）。deterministic ↔ D7 method = lint, automatable = full；assistive ↔ method = heuristic_review 或 runtime, automatable = partial。
