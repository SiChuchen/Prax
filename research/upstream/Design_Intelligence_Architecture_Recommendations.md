## 1. 执行摘要

研究支持建立 Design Intelligence，且支持的强度超出任务书预期：ISO 9241 标准体系、学术 MBUI 社区、企业设计系统三个互不隶属的体系独立收敛出同构的知识分层，这是"设计知识存在稳定结构"的最强证据 [N040][A059][C055]。但 L0–L7 八层设想需要四处实质性修正。第一，层数不是关键，硬边界只有一条——删除该陈述是否丢失设计意图；架构应重切为两域四带（语义域 S1 原则带/S2 结构带，渲染域 R1 惯例带/R2 实现带）加两个横切平面（验证、元知识），L0–L7 降级为域内检索粒度编号。第二，L2 产品宪法不是知识而是价值取向，应从知识分层中取出，作为冲突裁决非补偿层的治理制品。第三，L5 SDIR 的定位必须从"自动生成 IR"降为"设计决策记录层 + Agent 推理脚手架"，MBUID 四死因中 reification 不可判定性在 LLM 时代纹丝不动 [A048][A030]。第四，静态 S–E 证据分级经本次八维度实测失效（四组同级不一致），必须升级为 GRADE 式动态评级 + lex specialis/posterior 正交维度 + 强制时间戳 [N013][A033][A034]。

研究同时发现了任务书未预见的机会：意图/角色/重要性/可见性这一"关系层"是 tokens、组件库、pattern 库全部工业制品的公共盲区，四个研究维度独立指认同一空白——这是 Systemsmith 的独占定位，也是 SDIR 的 MVP 内容。下一步不要先建工具链（MBUID 的标准死法），而应先建知识获取流水线与 100–200 条带 owner、时间戳、反适用条件的规则存量，再执行化可判定子集，最后试点 SDIR。90 天计划见第 7 节。

## 2. L0–L7 分层审查

### 2.1 逐层审查

**L0 Human Perception（人类感知层）。** 证据支持其内容：Fitts、Hick–Hyman、工作记忆 4±1、前注意加工、Gestalt 分组全部是带边界条件的实证模型，是整套知识体系中证据最硬的部分 [N025][N010][N043][N028][N027]。但这一层混淆了一个概念：认知科学不是"设计知识的一层"，而是设计知识的**证据底座**。Agent 设计判断时消费的不是知觉模型本身，而是从模型导出的可判断命题（如"需要扫一眼察觉的信息必须编码在前注意通道上"）。修正：L0 不设为独立知识层，改为 S1 原则带每条原则强制携带的 `cognitive_anchor` 字段——Insight 2 的可还原性测试表明，能还原到认知/知觉不变量正是 universal 知识的判定标准，把这个判定标准做成字段比做成一层更有用。

**L1 Universal UX Principles（通用原则层）。** 证据支持，且已被 D3 操作化为 29 条原则、8 个域，每条带反适用条件与验证可能性标注。该层存在的问题是内部异质：实证模型（Fitts）、规范义务（WCAG POUR）、canon heuristic（Nielsen 系）混装。D5 的处置是正确的：域/带与知识类型是两个正交切面，S1 原则带内允许 empirical model 与 canon heuristic 并存，用类型字段区分而非再分层。此层保留，改名 S1 原则带。

**L2 Systemsmith Design Constitution（产品宪法）。** 这是原设想中概念混淆最严重的一层。产品宪法——"quiet/structured/dense/tool-like/readability-first"——不是知识，而是**价值取向与治理承诺**：它没有证据等级可言（不能说"高密度"比"极简"更正确），不随外部标准换代而演进，只能由产品决策修订。把它放进知识分层会产生两个实际危害：其一，Agent 会把它当可检索知识逐条引用，而它的正确用法是冲突裁决时的非补偿约束（视觉偏好不得覆盖宪法承诺）；其二，它会污染知识的证据分级——宪法条目既非 S 也非 E，无处安放。修正：L2 从知识分层中取出，定位为一份小的、人写的、版本化的治理制品，在冲突优先级链中占据非补偿层位置（见第 3 节），其修订本身走 Design Decision Record 流程 [B002][B003]。dim08 对冲突链的第三条失效风险（缺元规则——谁有权改链、链如何版本化）正是针对这一层的。

**L3 Product & Interaction Patterns（产品与交互模式层）。** 证据支持，但需修正两点。其一，独立公共 pattern library 的形态已死（Yahoo/welie/Quince 死亡链），存活形态是企业设计系统的 Patterns 层与 AI 交互模式类目 [A063][B038][C055][E009]；Systemsmith 的模式库能活的唯一理由是消费者换成了 Agent——一个不会转移兴趣的高频消费者。其二，模式层必须保留 Alexander 的 forces 与关系网络，否则退化为"截图 + 一句话"的最佳实践清单 [N055][A063]。D6 已给出七组字段 Schema 与 19 个首批模式。此层保留，归 S2 结构带。

**L4 Semantic Component Contracts（语义组件契约层）。** 证据支持其独立性，但范围要收窄。行为契约（键盘交互、焦点管理、states）已被 APG 31 个模式、Open UI、Zag.js 50+ 状态机工业化 [N001][N042][C061]——这一子层**不应自建**，引用即可；headless 生态用"行为复用"而非代码生成解决了跨平台一致性并获得主流采用 [C058]。真正的空白在意图子层：契约要素清单中 importance/priority/visibility 一行的现有形式化载体为空白，四个研究维度独立指认（Insight 4）。修正：L4 拆为"行为契约（外引 APG/Zag）+ 意图契约（自建，与 SDIR 词汇表共建）"。L4 与 L5 的关系由此明确：组件契约回答"这个组件一般怎样行为"，SDIR 回答"这个屏幕具体承诺什么"；SDIR 通过 `component_contract_ref` 单向引用 L4，任何反向引用都是分层泄漏。

**L5 SDIR（语义中间表示）。** 任务书立场"SDIR 不应成为另一种 CSS/JSX"经 D8 三重独立证据验证成立（高置信）：编码渲染细节的 UI 语言全部锁死单平台时代 [E026]；语义与渲染混装的系统全部死于复杂度过载 [N024]；LLM 端到端生成的不稳定根因正是缺意图中间层 [A061][A027]。但 L5 的定位必须降格：它不是编译器 IR（无确定性编译目标），而是**设计决策的显式记录层 + Agent 推理脚手架**，类比对象是 ADR 之于架构决策而非 JVM 字节码 [B003]。MBUID 失败四因的 2026 年再评估表明：工具链成本与"无活消费者"两因被 LLM 结构性缓解，生成天花板因 headless 模式部分缓解，但 reification 不可判定性（SingleChoice→radio 还是 dropdown 取决于空间/惯例/品牌 [A062]）纹丝不动——因此 Adapter 内的裁量点必须显式建模为一等公民，而非假装自动化掉。Figma-to-code 工具 20–40% 的实测手工修正率给出了裁量点的体量参照 [C013]。

**L6 Platform Profiles（平台画像层）。** 证据支持，Insight 9 给出了精确性质：平台设计系统（HIG/Material/Fluent）是"惯例的权威发布"，其知识价值在内容（44pt、8dp 网格、window size classes），scope 内为硬约束、跨 scope 自动降级 [B008][B013]。此层保留，归 R1 惯例带，强制 `platform + valid_from/valid_to` 字段。需要警惕的反模式：把平台视觉表现（M3 的色彩系统、HIG 的排版）上提为通用原则——target size 三体系（24px AA / 44pt HIG / 48dp Material）不可混用、不可互推 [N002]。

**L7 Runtime（运行时）。** 该层不是知识而是执行环境，不应出现在知识分层图中。它在架构中的正确位置是流水线的末端环节（产出可被 Visual QA 与可用性测试取证的真实界面）。修正：从知识分层移入流水线（第 4 节）。

### 2.2 任务书五问的明确回答

**分层是否合理？** 方向被三次独立收敛验证（ISO 9241 的概念→原则→呈现→元素→过程；Cameleon 的 Task→AUI→CUI→FUI；企业设计系统的 principles→guidelines→patterns→components→tokens），但八层暗示七条边界，而三个体系一致证明硬边界只有一条："删除该陈述是否丢失设计意图" [A059][N024]。结论：不推翻，重切为两域四带加两个横切平面。

**哪些层混淆了概念？** L0 混淆了证据底座与知识层；L2 混淆了价值取向与知识；L7 混淆了执行环境与知识；L4/L5 原设想未区分"已工业化的行为契约"与"空白的意图契约"。

**缺什么层/制品？** 四样：① 验证平面（X1）——lint/评审/用户测试三层验证对两域产出做判定，原设想散落在各环节未成体系；② 元知识平面（X2）——证据分级、冲突裁决、检索协议、生命周期，是"关于知识的知识"，原设想完全没有；③ 神话隔离库——已证伪命题（3-click rule、菜单≤7 项、Doherty 400ms）须物理隔离存储并供 Agent 主动反驳用户输入 [A032][B025][N030]，这是知识库的反向价值；④ 前沿带（frontier）——AI 交互模式、WCAG 3.0、M3 Expressive 等"变化速度 > 证据积累速度"的条目，须快速收录 + 强制过期 + 显式低权威 [N004][B021]。

**哪些已有成熟模型，不应自建？** DTCG tokens（2025.10 首个 stable，24+ 组织）[N032][N062]；APG/Open UI/Zag 行为契约 [N001][C061]；Agent Skills 三层渐进披露 [B006]；OPA/axe-core 的 policy-as-code 与零误报范式 [B028][B001]；组件成熟度模型（Primer 五级生命周期）[C023]；GRADE 证据分级 [N013][N014]；ADR/DDR 决策记录 [B002][B003]。

**哪些必须自建？** 关系层语义词汇表（region role/importance/visibility/density tradeoff——全部工业制品的公共盲区）；SDIR 最小词汇表与边界守护原则；冲突裁决记录与 DDR 回流机制；开发者工具特有模式（Run/Task 生命周期视图、Trace 瀑布、架构画布导航、live-tail 冻结、批量操作等 D6 认定的六项空白）；Golden Screens 基准界面集与产品证据（D 级）积累机制。

### 2.3 修正后的架构

```
┌─ 语义域 Semantic Domain（删除即丢失设计意图）
│   S1 原则带：可还原到认知/知觉不变量的普适原则与规范义务（D3 的 29 条）
│   S2 结构带：任务/IA/模式/关系层——设计意图的结构化表达
│      └ 关系层子带：role / importance / visibility / density（独占定位，SDIR 词汇来源）
├─ 渲染域 Render Domain（可形式化为值，删除只损表现不损意图）
│   R1 惯例带：平台惯例与规范数值（HIG/Material/Fluent，scope 绑定 + 有效期）
│   R2 实现带：DTCG tokens、组件视觉规格、APG/Zag 行为契约（外引为主）
├─ 横切平面 X1 验证层：lint（自动）/ Agent 评审+人复核（半自动）/ 真实用户测试（必须人）
├─ 横切平面 X2 元知识层：动态证据分级 / 冲突裁决+DDR / 检索协议 / 生命周期治理

└─ 流水线末端 Runtime → Visual QA → 可用性证据回流（D 级证据，驱动规则升降级）
```

## 3. 证据分级与冲突优先级修正

### 3.1 静态 S–E 分级的实测失效

任务书的 S/A/B/C/D/E 静态分级方向正确——把"来源权威"与"内容质量"绑定为检索时的置信过滤键是必要的。但本次研究本身就是一次大规模实测：八个研究代理共享同一套分级图例，仍产出四组"同一来源、不同级别"的矛盾。逐一解剖这四组矛盾，可以定位静态分级的三个结构性失效点。

**失效点一：分级语义的两个未定点。** NN/g 研究型文章被 dim03 赋 S（"Normative"）、被 dim02/dim04/dim01 赋 A；Shneiderman 1996 被 dim02 赋 S（"原始论文=S"）、被 dim03 赋 A（"HCI Canon=A"）。根因是两个规则从未统一：原始同行评审论文是否自动最高级？B 与 C 的边界画在哪（Atlassian 文档被 dim04 归入 Platform Canon 赋 B、被 dim06 归入 Mature Product Systems 赋 C）？交叉验证 §5 已裁决：S/N 保留给规范级文本与原始论文，NN/g 统一为 A，B 仅保留给 OS 平台级规范，企业设计系统统一为 C，Deque 厂商自研数据统一为 C。这个裁决本身说明：**静态分级只在语义边界被裁决后才可用，而边界裁决是一次性治理行为，不是分级制度的内生产物**。

**失效点二：authority 是时间的函数。** WCAG 3.0 草案一年三变，2026 年二手网络仍在传播已被放弃的奖牌制描述（冲突区 C3）——无日期戳的 3.0 描述已大面积失真；ISO 9241 系列 2024–2025 密集换代（112:2025、161:2025、171:2025），authority 不带版本即失真 [N004][N040]。静态分级没有时间维度，等于假定来源权威终身有效。

**失效点三：authority ≠ 证据强度。** Shneiderman 1996 是被引 9000+ 的 N 级原始论文，但作者本人 2026 年自述该文为 opinion piece、无实证结果，且存在反向 mantra [N019][E023][A021]；Deque 覆盖率报告样本巨大但无独立复现 [C002][D001]。单一标量无法同时表达"来源权威"与"实证强度"，高权威来源引用时必须能携带降格警示。

### 3.2 修正版：动态评级 + 正交维度 + 强制时间戳

修正方案借自循证医学与法学，三个机制协同（D7 已将其形式化进 Schema，此处给出架构级裁决）。

**GRADE 式动态升降级。** 静态级别降级为 `authority_initial`（初始级），随后按降级域（陈旧性、间接性、不一致性）与升级域（跨平台收敛、实证支持）动态调整 [N013][N014][N015]。两条子纪律：其一，证据确定性与推荐强度分离——authority 高不等于强制推行（GRADE 的核心分离）[N014]；其二，升降级命中必须留痕，Agent 检索到任何条目都能回答"它从什么级、因什么域、在什么日期变成现在这个级"。前沿层条目默认 D 级以下并强制 `expires_at`，是降级域的制度化应用。

**lex specialis / lex posterior 正交维度。** 静态优先级链只有 lex superior（上级优先）一个维度；法学规范冲突理论补充两个正交维度 [A033][A034]：lex specialis（适用范围更具体的规则优先）映射为 scope 匹配精确度——"专业工具高密度表格"的具体规则覆盖"保持界面简洁"的一般规则，跨级适用但不得突破非补偿层；lex posterior（后法优先）映射为版本时效——WCAG 2.2 覆盖 2.1、HIG 现行版覆盖存档版。同一来源的 authority 也是 scope 的函数：平台规范在本平台 scope 内是 B 级硬约束，跨平台引用降为 C（Insight 9），来源登记因此强制 `authority_scope` 字段。

**时间戳强制。** 每条规则强制 `source_version + source_date + review_by` 三元组：这是 lex posterior 的数据基础，也是陈旧性降级域的触发器。两条已制度化的入库硬规则直接来自交叉验证实测：WCAG 3.0 相关条目无日期戳视为不可信（C3）；覆盖率类数字必须绑定分母——"57.38%（issue 量）/31%（WCAG 2.2 A/AA 55 SC）/30%（WCAG 2.1 AA 50 SC）"三个口径入库时各自随行，否则下游引用必然混淆（C4）[C002][D001]。

### 3.3 冲突优先级链的评估与修正

任务书给出的链（User Task > Accessibility/Safety > Constitution > Universal > Platform > Pattern > Visual）方向正确：它把安全与合规放在视觉偏好之上，这与决策科学和本研究的证据一致。但 dim08 与交叉验证识别出四个失效风险，逐一修正如下。

**修正一：单一字典序改为分层混合模型。** 决策科学的证据是：字典序（非补偿）与加权加性（补偿）各有适用域，两阶段混合——先非补偿筛选、后补偿排序——是被验证的折中 [A010][A039]。落到链上：上段（User Task、Accessibility/Safety、Constitution）非补偿——任何视觉偏好的加权总和不得覆盖 WCAG 违规（合规 baseline 为 WCAG 2.2 AA [N005]）；下段（Universal vs Platform vs Pattern vs Visual）允许补偿式打分。纯排序的失效模式是同层内冲突无裁决依据；纯打分的失效模式是安全约束被大量低层偏好"积分兑掉"（补偿泄漏）。

**修正二："User Need 最高"加证据门槛。** 链顶最大的滥用风险是：任何需求都可声称是 user need，整条链被顶层架空。修正：确立 user need 只接受 D 级可用性测试证据（真实用户在真实任务上的行为数据），PM 主张不构成 need。这条门槛与 D 级证据积累机制（第 4.5 节）互为表里——没有证据积累机制，链顶就是空的。

**修正三：裁决必须场景化。** 交叉验证 C7 提供了活例：ISO 9241-110:2020 的 user engagement 原则与 HEART"企业场景 engagement 价值有限"之间的张力，不是事实矛盾而是场景依赖的价值冲突，全局优先级链给不出答案 [N045][A053]。修正：冲突不在原则层抽象裁决，而是落到 ATAM 式场景（source/stimulus/environment/artifact/response/response measure 六要素）上定位 tradeoff point [A007]。"安全确认 vs 操作效率"在批量删除与单条删除两个场景的裁决可以不同——场景化使冲突处理从全局一刀切变为条件规则。

**修正四：裁决沉淀与元规则。** 裁决产出 Design Decision Record（context/decision/status/consequences/supersedes [B002][B003]），裁决本身作为 D 级证据回流知识库——这使冲突处理从"每次重新争论"变为"可检索的判例积累"。同时补元规则：宪法修订流程、链本身的版本化、冲突裁决的记录义务；没有元规则的优先级链会在组织漂移中失效。

**修正后的完整优先级模型**（按执行顺序）：

| 步骤 | 机制 | 依据 |
|---|---|---|
| 0. 和谐解释 | 细化双方 `applies_when` 尝试消解——多数表面冲突是适用条件界定不清的伪冲突 | [A033] |
| 1. 非补偿层检查 | User Task（须 D 级证据确立）→ Accessibility/Safety → Constitution；下位任何组合不得覆盖上位 | [A010][A039][N005] |
| 2. lex specialis | 补偿层内，scope 匹配更精确的规则优先；跨级适用但不得突破第 1 步 | [A033] |
| 3. lex posterior | 同 scope 下版本更新的规则优先，以 source_version/review_by 为数据基础 | [A034] |
| 4. 补偿打分 | 同层同 scope 残余冲突，加权权衡 | [A010] |
| 5. 场景化裁决 | 上述步骤未决，落 ATAM 六要素场景定位 tradeoff point | [A007] |
| 6. DDR 沉淀 | 裁决记录为 Design Decision Record，回流入库成为 D 级证据 | [B002][B003] |

## 4. 流水线设计

### 4.1 全链路总览

流水线的设计原则是任务书"Knowledge → Retrieval → Reasoning → SDIR → Validation → Implementation"骨架的展开，每一环节标注输入/输出/知识来源/自动化程度。自动化程度取三值：**自动**（确定性执行，零误报范式）、**Agent+人**（LLM 初筛或起草，人工复核或终裁）、**必须人**（本质上不可自动化，机器只能辅助取证）。三值的划分依据是 Insight 5 的自动化三段式：地板可确定性执行；中间带 LLM 可做但一致性 κ≈0.50、严重性判断 α≈0，必须带人工复核标记 [C006][A017]；天花板之上（严重性排序、权衡裁决、真实体验）机器不可判定——usability 在规范上被定义为 outcome 而非 property，宣称可用性必须绑定 specified users/goals/context，否则命题逻辑上不可证伪 [N040]。

| 环节 | 输入 | 输出 | 知识来源 | 自动化程度 |
|---|---|---|---|---|
| 1. 需求理解 | 自然语言需求、任务背景 | Task/Context/User Model（用户类型×任务类型×密度×平台） | IAN/COG 域、OOUX 方法（实践共识，中等置信）[B026] | Agent+人 |
| 2. 知识检索 | Task/Context/User Model | 相关原则、模式、惯例候选集（带证据链） | 规则库（B 三层披露 + hybrid search）[B006][B029] | 自动（检索）+ Agent（相关性初判） |
| 3. 信息架构 | 领域对象集、任务清单 | 对象模型、导航结构、页面清单 | S2 结构带：四系统 [A020]、object-first | Agent+人 |
| 4. 模式选择 | 页面任务画像 | 模式组合方案（含 alternatives 裁决记录） | S2：Pattern Library（forces/tradeoffs）[N055] | Agent+人 |
| 5. SDIR 编写 | 模式方案、意图陈述 | SDIR 文档（区域角色/重要性/可见性/密度意图 + 裁量点清单） | 关系层子带词汇表、模式引用 | Agent 起草 + 人审 |
| 6. 设计验证 | SDIR + 候选实现 | 验证报告（lint 结果/评审发现/待人工项） | X1 验证层、规则的可判定子集 | 分层（见 4.3） |
| 7. 平台适配 | SDIR + context of use | 各栈具体布局与控件选型（CUI 级方案） | R1 惯例带、MARIA 式细化表 [A062] | Agent+人（裁量点） |
| 8. 运行时实现 | CUI 方案、tokens | 可运行界面（FUI） | R2 实现带、组件库 | 自动（工程） |
| 9. Visual QA | 渲染产物截图/DOM | 视觉缺陷清单（六病因诊断） | 关系层规则、显著性模型 | Agent+人（初筛可，终裁不可） |
| 10. 可用性证据 | 真实用户任务测试 | D 级产品证据（Golden Screen 基线、任务指标） | EVL 域方法论 [A053][A022] | 必须人 |

### 4.2 知识组织：B + C 混合路径

环节 2 的检索基础设施采用 D7 的推荐路径：**Schema B 组织 + Schema C 执行化子集，Schema A 起步采集**。理由不再重复论证，只列出架构后果。第一，三层渐进披露（L1 索引约 100 token 常驻可枚举 → L2 正文 <5k 触发加载 → L3 例证与验证档案按需读取）是硬约束而非优化项：LLM 对长上下文中部信息的利用呈 U 形曲线下降 [A026]，18 个前沿模型全部随输入变长而性能退化 [C031]，知识库超过约 200k token 即必须检索 [B005]——一个数百条规则的底座必然越过这一阈值。第二，`applies_when` 一身三职：frontmatter 触发条件、metadata 过滤键、lex specialis 匹配键——它是全套架构中杠杆最高的字段，其质量决定检索精度与裁决正确性。第三，三层必须同源生成（trigger 与 applies_when 禁止手工双写）并在入库时做 L1↔L2 的 entailment 一致性检查 [A041]，否则检索会在规则修订中静默失灵。第四，机器可判定子集（token 引用合法性、对比度、target size、组件属性完备性）编译为 policy-as-code 进 CI，遵循 axe-core"零误报 + 不确定转人工"范式 [B001][B028][D005]；判定不了的交给 soft heuristic 通道，硬编码 LLM 可推理的知识会重演专家系统的知识获取瓶颈与脆性 [C019][D003]。

### 4.3 验证三层

环节 6 与 9 合并为 X1 验证平面，分三层，每层有明确的置信度纪律。

**第一层 lint（自动，地板）。** 数值/几何/引用类检查：对比度 4.5:1 与 3:1、target size 24px、token 引用合法性、组件属性完备性、间距基数、tabular-nums、词典驱动的术语一致性 [N005][N002][N032][B037][C030]。可零误报执行，可 fail 构建。其覆盖面要诚实声明：自动化无障碍检测按 issue 量口径约 57.38%、按 SC 条数口径约 30–31% [C002][D001]——lint 是必要的地板，不是充分的验证。

**第二层 Agent 评审 + 人复核（半自动，中间带）。** 启发式问题存在性、模式适用性初判、视觉层级成立性。LLM 检测一致性 κ≈0.50，可作初筛 [C006]；但严重性排序 α≈0 [A017]、评委存在系统性 position/verbosity/self-preference 偏差 [A028]、54.1 万条判断的大规模复测发现机会校正后区分度缩水 33–41 个百分点 [C033]——**LLM 评审初筛可、终裁不可**。工程上强制偏差缓解协议：成对比较优先（绝对打分与批量排序显著发散 [A055]）、顺序交换复评、rubric 锚定、与人类标注样本季度校准（κ 低于门槛即暂停自动评审）。所有本层输出强制携带 needs-human-review 标志。另有一条取证纪律：截图级评审"产出流畅但证据薄弱的批评"，因为大量可用性失败是交互性的（禁用控件无解释、表单静默拒绝、破坏性操作隐藏后果）——可靠评审要求操作控件、观察状态转移、测试错误恢复路径，即 runtime 取证是评审的前置条件 [C005][A004]。

**第三层真实用户测试（必须人，天花板）。** learnability、真实任务效率、满意度、心智模型匹配、默认值合理性——全部是 outcome 类命题，只在 specified users/goals/context 下可证伪 [N040]。合成用户不能替代真实用户研究，仅可用于 desk research 与假设生成（NN/g 2024 + ACM AHs 2025 双权威源，高置信）。这一层是流水线的终点也是知识回流的起点。

### 4.4 裁量点：流水线中的显式人工接口

环节 5 与 7 之间的 Adapter 不是黑盒。SDIR 不承诺语义到布局的确定性映射，而是在 Adapter 接口处声明裁量点（decision point）：每个裁量点记录影响因子（空间预算、平台惯例、密度意图）、默认启发式、何时升级人工。这与 axe-core"不确定项转人工"是同一置信度处理范式在生成侧的投影 [B001]，也是对 MBUID 第四死因（reification 不可判定）的制度性接纳。裁量点的审计日志是第 6 节风险登记中"Agent 过度自信"的早期信号源：裁量点被默认启发式静默接管的比例上升，意味着人工复核在被架空。

### 4.5 D 级产品证据的积累与回流

流水线的最后一环把使用证据变成知识资产，形成闭环。机制有三。**Golden Screens**：一组内部基准界面（首批 10–20 屏，覆盖 master-detail 工作区、高密度数据页等 Systemsmith 典型形态），作为模式入库与升级的实证门槛——模式在其 `validation` 字段的 empirical 检查须在 Golden Screens 上不低于基线方可升 stable。**可用性测试回流**：真实用户测试产出的任务指标（成功率、时间、错误率）登记为 D 级证据，绑定 specified users/goals/context 与日期；它证明的是"对本产品用户成立"，泛化引用时自动降级。**证据驱动规则升降级**：D 级证据是 GRADE 升级域（实证支持）与降级域（不一致性）的输入——当产品证据与某条规则冲突时，触发该规则的复审而非静默服从规则；当某条 draft 规则被产品证据与第二独立来源共同支持时，满足 stable 的"≥2 独立来源"条件。这一闭环直接回答任务书的"Usability Evidence"环节：它不是验收步骤，而是知识底座的生命线——知识制品的死亡率与维护机制强相关、与初始质量弱相关（Insight 7），D 级证据积累机制就是这个维护机制的主体。

## 5. Q1–Q15 逐条回答

**Q1 是否存在足够成熟的跨技术栈理论支撑 Design Intelligence？——是，但支撑是分层的：原则层成熟，关系层空白，而空白即机会。**
原则层的成熟度有硬证据：ISO 9241 标准体系、学术 MBUI（Cameleon 四层）、企业设计系统（principles→tokens）三个互不隶属的体系独立收敛出同构分层 [N040][A059][C055]；认知与知觉侧的实证模型（Fitts、Hick–Hyman、工作记忆、前注意加工）跨越平台换代仍然成立，因为它们锚定的是人类不变量而非技术 [N025][N010][N043][N028]。规范侧，WCAG 2.2 AA 是 2026 年唯一可作为合规 baseline 的无障碍标准，ISO 9241-171:2025 已内置其映射 [N005][N052]。但要精确指出不成熟的区域：意图/角色/重要性/可见性这一关系层在全部工业制品中没有载体（Insight 4）；AI 交互、WCAG 3.0 等前沿层变化速度大于证据积累速度，规范制定者明确缺席（ISO 9241-110:2020 自述不覆盖 AI 细节）[N045][N004]。结论：跨栈理论足以支撑 Design Intelligence 的骨架，且恰好标出了它的差异化位置——原则层靠整理与标注，关系层靠自建与验证。

**Q2 哪些知识应进入 Universal Layer？——D3 的 29 条，入选标准是四重测试。**
入选命题须同时满足：① technology-independent（ISO 9241-110 对原则的自我定位 "independent of situations of use, application, environment or technology" 是规范参照 [N045]）；② 有标准级或 canon/原始研究级证据；③ 可陈述为可判断命题——写得出 `applies_when` 与 `does_not_apply_when`，写不出反适用条件的不收；④ 不是另一条原则的换皮。操作测试是可还原性：能还原到认知/知觉不变量者入（工作记忆外化、知觉分组、前注意编码、再认优于回忆、错误预防、可逆性、信息气味、信噪比等 29 条）；能还原到硬件/OS/年代者降入惯例层；无法还原到一手来源者入神话隔离库。系统性去重是入选过程的副产品："一致性"家族（Nielsen #4、Shneiderman #1、ISO conformity、Jakob's Law、HIG Consistency）合并为内部/外部两条；CRAP 拆解后仅两条可上溯感知证据；Nielsen #8 以信噪比纠错性重述替代流行的"少即是多"误读 [A050][A024][N045][A054]。

**Q3 哪些只能是 heuristic？——判据是"可违反性 + 判断依赖性"，并须显式标注证据弱点。**
一条知识落入 heuristic 层（由 D4《UX_Heuristics_Draft.md》承载：31 条评审启发式 H-01…H-31（含神话隔离区 9 条与 HE 执行规程）；D3 §9.2 降级记录保留作边界设计史说明。）的条件：有权威出处但非定律；适用面广但存在合法反例；其应用需要评估者按语境裁量而非机械执行。典型条目：Nielsen 十条（canon，1994 年来未实质变更 [A050]）、overview-first mantra（作者自述 opinion piece、存在 search-first 反向 mantra [N019][E023][A021]）、progressive disclosure（源头作者自认 "empirical research lacking" [B042][B043]）、45–75 CPL 行宽与 type scale（排版工艺共识 + 弱实证）、command palette（跨产品主流化是事实，无期刊级实证 [C057]）、OOUX/ORCA（实践共识，无同行评审 [B026]）。与 universal 原则的分界操作化为两点：证据强度停留在 B/C 级或实证基础被原作者自认薄弱的候选一律降级；heuristic 条目必须携带已知例外与置信度标注——overview-first 条目必须随附 search-first 反例，否则就在制造新神话。

**Q4 哪些属于 platform convention？——判据是"可还原到具体平台/OS 版本/硬件约束"，scope 内硬约束、跨 scope 自动降级。**
可还原性测试的第二分支：一条陈述若能还原到特定平台生态（而非人类不变量），即为 platform convention。判据三要素：绑定 `platform + version + valid_from/valid_to`；在 scope 内是硬约束（iOS 应用应守 44pt）；跨 scope 引用自动降级为参考。典型示例：target size 三体系（WCAG 24px 是规范地板、HIG 44pt 与 Material 48dp 是平台惯例，三者单位不同、不可混用、不可互推）[N002][B008][B013]；8dp 网格与 window size classes [B013]；M3 color roles 与 on-配对（思想可迁移、数值不可迁移）[B023]；Fluent density modes [B014]；SF Symbols 语义。必须警惕的反模式是把平台视觉表现上提为通用原则——M3 Expressive 的"4 倍识别速度"是厂商研究、无独立复现 [B021]；Apple HIG 2026 首页三原则是平台语境的价值表述，其 universal 成分已并入原则带，Harmony 等表述不入选。平台设计系统是"惯例的权威发布"，与作为"治理机制实证样本"的企业设计系统是两种知识物种，消费策略不同（Insight 9）。

**Q5 哪些应成为 Product Pattern？——判据是"反复出现的问题 + 显式权衡 + 可组合"，指向 D6 的 19 条首批清单。**
一条知识成为 pattern 而非原则或组件的条件：它回答"在什么场景下、为什么问题、用哪种组合、代价是什么"——四元组 problem/context/forces/solution 缺一不可，其中 forces 是精髓：没有 forces 的条目不得入库 [N055][A063]。组件回答"用什么实现"，模式回答"什么时候为什么"；template 是模式的一次实例化，模式是生成无数 template 的解的核心。D6 首批 19 条按"证据成熟度 × 产品域覆盖率"选取：List→Detail→Inspector、Command Palette、Faceted Filter、Global Search、Overview→Filter→Detail、Undo>Confirmation、Empty State 等，每条带证据分级、反模式与三类验证检查 [A019][C055][C036]。入库双门槛：至少一项 C 级工业验证或 B 级平台验证（纯学术 canon 不足以单独支撑 stable），且升 stable 前须通过 Golden Screen 内部确认。六类开发者工具特有空白（Run/Task 生命周期视图、Trace 瀑布、架构画布导航、live-tail 冻结、批量操作、AI 生成标识与再生）以 draft 状态先行登记，待产品证据积累后升级——"借得动的先借，借不动的先立档"。

**Q6 哪些规则可以自动验证？——lint 子集的共同特征是"数值/几何/引用可判定 + 零误报可承诺"，覆盖率须诚实声明。**
可自动验证的规则满足三个特征：判定是数值、布尔或集合包含关系（对比度 ≥4.5:1、target ≥24px、token 引用是否在白名单内）；判定不依赖语境与意图；不确定情形可安全地转人工而非误判（axe-core 范式）[B001]。具体清单：对比度与色彩数值、target size、间距基数与网格对齐、tabular-nums 等 CSS 特性、token 引用合法性、组件属性完备性（aria 绑定存在性）、词典驱动的术语/标签一致性、键盘遍历断链的脚本化检出 [N005][N002][N032][B037][C030]。覆盖率必须绑定分母诚实声明：自动化无障碍检测按 issue 量口径约 57.38%，按 WCAG 2.2 A/AA 成功准则口径仅 17/55≈31%，按 WCAG 2.1 AA 口径约 30% [C002][D001]；且 2026 年仍有 95.9% 首页存在可自动检出的失败 [A001]——lint 能抓住的失败远未被抓完，这既是 lint 价值的证明也是其边界的证明。凡声称"自动验证体验质量"的功能应在架构上被拒绝。

**Q7 哪些必须通过视觉判断？——关系层与审美层；LLM 视觉评审初筛可、终裁不可。**
必须经视觉通道判断的知识集中在关系层：视觉层级是否成立、密度是否克制、装饰是否与信息竞争、"这个页面是否专业"。这些判断的自动化边界已被量化：LLM 启发式评估的检测一致性 κ≈0.50，可作初筛 [C006]；但严重性排序 α≈0 [A017]；评委存在 position/verbosity/self-preference 系统性偏差 [A028]；54.1 万条判断的复测显示机会校正后区分度缩水 33–41pp、评委排名跨 benchmark 移动多达 14 位 [C033]；GPT-4 对 UI mockup 的评审随设计迭代改进而退化，不适合作迭代评审工具 [A004]；截图级评审"产出流畅但证据薄弱的批评"，可靠评审必须操作控件、观察状态转移、走错误恢复路径 [C005]。结论：视觉判断环节的正确形态是"LLM 初筛（带 rubric 锚定与成对比较协议）+ 人工终裁 + runtime 取证"，且所有 LLM 评审输出强制携带 needs-human-review 标志。把 LLM 视觉评审当终裁，等于用 α≈0 的工具做严重性排序。

**Q8 哪些必须真实用户测试？——一切 outcome 类命题，这是规范要求而非谨慎偏好。**
usability 被 ISO 9241-11:2018 定义为 effectiveness/efficiency/satisfaction 在 specified users/goals/context of use 下的达成程度——它是使用的结果而非产品的属性，不带用户/目标/场景绑定的可用性宣称在逻辑上不可证伪 [N040]。因此以下问题只有真实用户测试能回答：learnability（新手多快形成可用心智模型）；真实任务效率（专家 time-on-task、密度收益终裁）；满意度（SUS/UMUX-LITE [A056]）；心智模型匹配（卡片分类与 tree testing——后者须选保留路径历史与回退的变体 [A058][N033]）；默认值合理性（行为数据分析 + 测试）；信号显著性是否足够（变更视盲问题无法自我报告 [N008][N009]）。合成用户不能替代真实用户研究，仅可用于 desk research 与假设生成（双权威源，高置信）。这层测试同时是 D 级证据的生产线：确立 user need 的证据门槛（冲突链顶防架空条款）只能由它满足。

**Q9 设计原则如何转化为 Agent 可执行知识？——D7 的三 Schema 评估与 B+C 混合路径。**
转化不等于"把原则写成规则"。D7 评估了三种组织与消费协议：Schema A 扁平条目（采集成本最低，适合作录入格式）；Schema B 三层渐进披露（映射 Agent Skills 工业事实标准，解决 context 经济）[B006][D002]；Schema C policy-as-code 分层（可判定子集确定性执行）[B028][B001]。推荐路径 B 组织 + C 执行化子集、A 起步采集，分三步迁移：先用扁平条目跑通知识获取流水线并积累 100–200 条 reviewed 规则；再从 scope/applies_when 机械生成 L1 触发层并上线 hybrid search + metadata filtering（同源生成，禁止手工双写）[B029][A041]；最后对 `automatable=full` 的规则生成 match/assert policy 按"先 warning 后 error"接入 CI [D005]。转化的关键纪律四条：每条原则拆出可判定子集与不可判定部分，前者编译为 policy、后者保留为结构化评审 rubric；规则引擎只承载可判定子集，LLM 可推理的不硬编码（专家系统死因）[C019]；provenance 生成时随行（statement←rationale←evidence←source），验证阶段逐条 entailment 检查——引用≠支持，30–50% 的 LLM 陈述在有来源时仍缺乏充分引用支持 [A040][A041][A042]；每条规则强制 owner、does_not_apply_when、review_by，无此三字段不得进 stable。

**Q10 是否应建立 SDIR？——应，但定位为设计决策记录层 + 推理脚手架，而非全自动生成 IR。**
支持的证据链四点。需求侧：LLM 生成不稳与 design-to-code 质量瓶颈的根因被多项独立研究定位为缺意图/语义中间层——商用工具均无法生成响应式代码、难以识别元素意图 [A061]；意图澄清把平均修改轮次从 6.1 降到 2.6 [A027]；无中间表示的端到端生成质量随模型版本漂移 [C032]（Low，方向与学术研究一致）。供给侧：关系层是全部工业制品的公共盲区（Insight 4），SDIR 是差异化而非重复建设。时机侧：MBUID 四死因中三个被 LLM 时代结构性缓解，剩余一个（reification 不可判定）由裁量点显式建模接纳。生态侧：W3C UI Specification Schema CG（2025-08）表明该方向正在重新标准化 [N035]；截至 2026-08 无任何主流产品实现"证据分级 + 冲突裁决 + 可验证语义 IR"完整形态，Figma 自动 rules file 最接近但无分级与冲突解析 [C011]。同时，定位声明必须写入项目宪法：**SDIR 类比 ADR 而非编译器 IR**；其价值度量是设计意图跨平台保真度、Agent 输出可解释性与可回归性，而非"自动生成了多少代码"——后者正是 MBUID 用错的、并因此死亡的指标 [B003][A048]。

**Q11 SDIR 的正确抽象边界是什么？——边界守护原则 + 最小词汇表 v0 + 绝不进入清单。**
边界守护原则：SDIR 中不允许出现任何无法在非视觉模态下保持意义的陈述。操作化为删除测试：删掉该陈述，设计意图是否受损？`importance: supporting` 删掉则 Adapter 无法在移动端做降级决策（属 Semantic）；`display: flex` 删掉意图可由语义重新导出（属 Render）[A059]。最小词汇表 v0 只含：archetype（引用 Pattern Library）、intent、density_intent、regions[].{id, role, importance, visibility, interaction}、pattern_ref、component_contract_ref——每个字段都有先例祖先（importance → TERESA Hierarchy 算子 [A009]；interaction → MARIA 交互器分类 [A062]；visibility → Cameleon context of use [A059]），没有生造概念。绝不进入清单：像素/几何/坐标；布局算法与容器类型；样式值（用 DTCG token 引用 [N032]）；控件选型（radio vs dropdown 是 Adapter 裁量 [A062]）；具体文案（UIML content 分离原则 [A049]）；平台 API 痕迹（XUL 死线 [E026]）；动画参数；当前状态值（IR 记条件不记状态）。两个易误判字段：spatial_priority 合法（顺序承诺非坐标）；control: dropdown 非法（控件选型是 reification 决策）。边界守护原则同时是治理工具：任何字段提案提不出非视觉模态消费场景即一票否决——这把"加不加字段"从品味之争变成可裁决的合规测试。

**Q12 Component Contract 是否应独立于代码？——应，且其可行性已被 APG/Zag 部分验证；但意图层空白须自建。**
独立于代码的组件契约在 2026 年已有工业化解：APG 31 个模式定义了框架无关的键盘交互与焦点契约 [N001]；Open UI 逐控件推进词汇标准化 [N042]；Zag.js 的 machine/connect 两段式——一次定义行为状态机，经 adapter 投影到 React/Vue/Solid 各框架——证明"核心语义一次定义、表现层多端适配"工程上成立，50+ 组件状态机在生产使用 [C061]；headless 生态的主流采用证明"行为复用"比"代码生成"更能解决跨平台一致性 [C058]。因此行为契约子层不自建、直接引用。但契约要素清单中 importance/priority/visibility 一行的现有载体为空白——这是意图子层，必须自建，且应与 SDIR 词汇表共建（同一套 role/importance/visibility 词汇）。引用方向固定单向：tokens ← 组件契约 ← 模式 ← SDIR 实例，任何反向引用即分层泄漏。APG 示例同时给出了自建意图层的质量标杆：范围克制者生存——APG 只定行为不定布局，恰是其工业化成功的原因；意图层的词汇表也必须克制（核心集冻结 + 扩展集注册制），否则重蹈语义词汇表膨胀。

**Q13 Design Intelligence 与传统 Design System 的正确关系是什么？——大脑与工具箱；语法层与词汇层；单向引用。**
两者是不同抽象层级的制品，不竞争、不替代。Design System（tokens、组件库、文档）是**工具箱与词汇层**：它管值（DTCG tokens [N032]）、管零件（组件）、管行为契约（APG/headless），DTCG 的自我定位"交换格式而非架构格式"精确划出了它的边界——tokens 不能表达组合关系与适用语境 [N029]。Design Intelligence 是**大脑与语法层**：它管"什么时候为什么"——原则、模式、关系层语义、冲突裁决、证据分级，是组装词汇的语法与判断依据。具体关系三条：其一，引用单向——Design Intelligence 引用 Design System 的制品（token 层、契约、模式实现）作为下游执行资源，Design System 不反向依赖知识库；其二，机制反哺——企业设计系统是"治理机制的实证样本"（Insight 9），其成熟度模型、弃用路径、贡献治理应被知识库自身的生命周期管理直接借用 [C023]；其三，边界互不侵占——Design Intelligence 不发布组件、不定义色值（那是 R2 实现带的外引内容），Design System 不承载意图与优先级语义（那是关系层，其空白正是 Design Intelligence 的定位）。对 Systemsmith 产品而言：Design System 让它看起来一致，Design Intelligence 让它被正确地设计。

**Q14 如何防止"理论正确但产品很丑"？——承认知识不能替代视觉验证，并把视觉质量拆成可 lint、可诊断、可基准回归的三层。**
"理论正确但产品很丑"的机制是：组件正确 ≠ 屏幕专业，因为专业感存在于元素之间的**关系层**（对齐、节奏、层级梯度、语义一致性），而这一层恰是组件库与原则条文都不覆盖的（Insight 4、dim04 A7）。防御体系四层。其一，关系层规则的 lint 化：dim04 的六病因诊断清单中三项可自动检测——对齐失锚（边界盒坐标一致性 lint）、节奏混乱（spacing token lint）、数字排版业余（tabular-nums CSS feature lint）[B034][B037]；两项半自动——层级不清（截图显著性分析 + LLM 初筛）、装饰与信息竞争（色彩审计 + 视觉判断）；容器滥用可由 common region 计数半自动检出 [A018]。其二，Golden Screens 基准回归：一组内部基准界面作为视觉质量的回归基线，任何知识库或组件变更不得使 Golden Screens 的六病因诊断结果劣化。其三，Visual QA 作为流水线独立环节（第 4.1 节环节 9）：LLM 视觉评审初筛 + 人工终裁 + runtime 取证，其输出与 lint 结果合并进验证报告。其四，诚实边界：色彩气质、品牌感、微妙空间节奏属审美裁量，机器不可终裁——这层质量的保证机制是"人审 + Golden Screen 基线 + 宪法非补偿约束"，而不是更多规则。把审美写成 hard rule 会系统性压制有实证支撑的密度与效率知识（D7 反模式清单），方向恰恰相反。

**Q15 下一步真正应该先实现什么？——先流水线与存量，后执行化，最后 SDIR；工具链最后。**
**P0（第 1–6 周）：知识获取流水线 + 首批规则存量。** 以 Schema A 为录入格式，从 WCAG 2.2/ISO/HIG 与 D3 的 29 条原则、D6 的 19 个模式半自动抽取 + 人工审定，目标 100–200 条 reviewed 规则；强制 owner、does_not_apply_when、source_version、review_by 四字段；同步建立神话隔离库首批（3-click、7±2、Doherty）[A032][B025]。理由：专家系统与 pattern library 的共同死因是没有知识获取管线，管线是一等交付物 [C019][A063]；且后续一切（检索、lint、SDIR）都消费这份存量。依赖：无，立即启动。
**P1（第 5–10 周）：检索触发层 + lint 执行化 + Golden Screens v0。** 从 A 条目机械生成 L1 索引，上线 hybrid search + metadata filtering [B029]；可判定子集（对比度、target size、token 引用、对齐、间距基数）编译为 policy 进 CI（先 warning）[D005][B001]；建 10–20 屏 Golden Screens 与六病因诊断基线。依赖：P0 的规则存量。
**P2（第 9–13 周）：SDIR 试点 + 冲突裁决机制运转。** 选 2–3 个真实页面手工编写 SDIR，由"资深前端 + Agent"组合各自实现 Desktop/Mobile 版，通过非视觉模态测试与语义保真度检查 [A059]；冲突裁决管线（和谐解释→层级→lex specialis→场景化→DDR）在真实设计评审中运转并沉淀首批 DDR [A007][B003]。刻意推迟：完整 SDIR 工具链（编辑器、CI、多 Adapter）只在试点三条件通过后立项——MBUID 史反复证明"先建工具链、再找用户"是死亡路径 [N024]。

## 7. 90 天行动建议

以下计划按先后依赖排列，每项标注产出物与验收标准。总原则来自 Insight 7：知识制品的死亡率与维护机制强相关——90 天的目标不是"建成知识库"，而是**建成一条能持续生产、审定、退役知识的流水线，并让它运转起来**。

**第 1–2 周｜制度先行（无依赖，立即启动）。** ① 发布全局分级语义裁决：N/A/B/C/D/E 边界按交叉验证 §5 固定（N=规范文本与原始论文；A=canon 与权威机构一手研究；B=OS 平台级规范；C=产品级系统与厂商自研数据；authority_scope 字段上线）。② 发布两条入库硬规则：前沿条目强制日期戳与 expires_at；覆盖率类数字强制绑定分母。③ 指定知识库 owner 团队与规则 owner 分配机制——无 owner 的规则不得入库。产出：治理章程 v1（含宪法初稿与冲突链元规则）。

**第 3–6 周｜知识存量建设（依赖①的分级语义）。** ④ 以 Schema A 为录入格式跑通"标准监测 → 半自动抽取 → 人工审定"流水线，源清单：WCAG 2.2 hard rules、ISO 9241-110/-112 原则、D3 的 29 条原则、D6 的 19 个模式、神话隔离库首批 5 条。⑤ 验收：100–200 条 reviewed 以上规则，每条具备 owner、does_not_apply_when、source_version、review_by 四字段；抽查 20 条的 provenance 链完整率 100%。⑥ 同步启动 Golden Screens v0：选 10–20 屏典型形态（master-detail 工作区、高密度数据页、Trace 瀑布、日志 Explorer），建立六病因诊断基线。

**第 5–8 周｜检索与执行化（依赖④的存量，可与⑥并行）。** ⑦ 从 A 条目机械生成 L1 索引（trigger 与 applies_when 同源生成），上线 hybrid search + metadata filtering，入库闸加装 L1↔L2 entailment 一致性检查 [A041]。⑧ 可判定子集执行化：对比度、target size、token 引用、对齐锚定、间距基数、tabular-nums 编译为 policy，接入 CI 的 warning 档（不 fail 构建）[D005][B001]。验收：lint 在 Golden Screens 上零误报；检索抽检（20 个任务画像）候选集召回人工评分达标。

**第 9–12 周｜SDIR 试点与裁决机制运转（依赖⑦⑧）。** ⑨ SDIR 试点：选 2–3 个真实页面手工编写 SDIR，"资深前端 + Agent"组合实现 Desktop 与 Mobile 两版，验收三条件：两版形态不同但语义承诺全部可追溯回 SDIR 字段；非视觉模态测试通过（语音摘要可复述设计意图）；编写成本不超过同等设计文档 [A059]。⑩ 冲突裁决管线在真实设计评审中运转：至少完成 3 例完整流程（和谐解释→层级检查→lex specialis→场景化→DDR），沉淀首批 DDR 并回流入库 [A007][B003]。⑪ 验证三层联通演练：lint 报告 + LLM 评审（带偏差缓解协议）+ 一轮真实用户测试（≥5 名目标用户，任务计时），产出首批 D 级证据并触发至少一次规则升降级。

**第 13 周｜复盘与门控决策。** ⑫ 对照 R1–R10 的早期信号逐项检查；对照试点三条件决定 SDIR 工具链是否立项（默认不立项，除非三条件全过且词汇表核心集冻结）；发布 v1.1 计划：P1 项（Confirmation、Loading/Skeleton、Modal vs Non-modal、Wizard、Settings Hub-and-Spoke、Dashboard vs Explorer、Optimistic UI、AI 生成标识）入库与第二批 Golden Screens。
